## Context

See proposal.md - Why/What Changes for the motivation and change list. Relevant current-state facts that shape the approach:

- The design system lives entirely in one file, `extension/src/ui/panel.css` (custom properties on `:host`/`:root`, then BEM-ish `.c500-*` component classes), consumed by `TabRoot.tsx` and the shared components under `extension/src/ui/components/`.
- `DeckCard.enrichment.colorIdentity: string[]` (Scryfall color-identity array) is already present on every enriched card — no new data plumbing is needed for the color-identity rail or chart recoloring.
- There is no floating overlay panel anymore (`content-script.ts` mounts no UI); `.c500-panel`'s container/gauge/legality/export rules in `panel.css` are dead, though two of its sub-classes (`c500-panel__mark`, `c500-panel__format`) are still used by `TabRoot.tsx`'s header.
- The extension ships no bundled web fonts and loads no external font CDN; all three current type roles (`--c500-font-display`, `-body`, `-mono`) are system-font stacks.

## Goals / Non-Goals

**Goals:**
- Establish one token system (color + type) that reads as a deliberate "budget ledger" identity while functionally encoding Magic's own color pie, not a generic re-theme.
- Fix the two concrete layout problems named in the proposal (duplicate gauges, undifferentiated Commander) without touching any component's underlying data/logic.
- Keep every existing spec-required behavior (view toggle, drag-and-drop, illegal/over-budget markers, live recomputation, etc.) working unchanged underneath the new markup/styling.

**Non-Goals:**
- No light/dark theme *toggle* — one committed look, full stop. That committed look pivoted mid-change from light "parchment" (`color-scheme: light`) to a dark "Night Ledger" neutral (`color-scheme: dark`) in response to direct feedback asking for something more modern and minimalist; there is still only one theme, not two to switch between. The `color-scheme` change also affects native form-control rendering (the format/grouping `<select>`s, the quantity `<input type="number">`) — browsers render their default OS-native widget chrome in dark mode once this is set, no extra styling needed for that part.
- No new web font dependency — type character comes from weight/scale/spacing on existing system-font stacks, not a new typeface or CDN request.
- No change to card-art resolution (`resolveCardArt`/`card-art.ts`) — only the frame/chrome around artwork changes.
- No per-color pip breakdown for multicolor cards (e.g., split rail) — multicolor cards get the single gold rail, mirroring a real Magic card's gold frame.

## Decisions

**"Night Ledger": a dark, cool-neutral pivot away from the parchment direction, not just a re-tint of it.** Direct feedback asked for "an even more modern and minimalist look," specifically on color. The original warm-parchment base (`#ece0c8`) and its serif-headed "budget ledger" execution — like the near-black-plus-single-accent and broadsheet-hairline looks it deliberately avoided at the start — turned out to be its own kind of default: a cream-and-serif combination that reads as considered but is in fact one of the handful of looks AI-generated design clusters around regardless of subject. The fix isn't a darker cream or a different accent color on the same warm base; it's a genuine pivot to a near-black, cool-neutral canvas (`--c500-bg: #17171b`, `--c500-bg-raised: #1f1f24`) with muted, desaturated accents rather than saturated ones — paired with dropping the serif entirely (see the typography decision below) and removing the ledger tape's divider lines, so the only color doing real work is the mana-identity/status system itself. Minimalism here means *removing* decoration (serif contrast, divider lines, saturation) so the functional color — the rail, the gauges, price — is the only thing that reads as an accent.

**Token names drop the "ink"/"paper" metaphor along with the parchment concept itself.** `--c500-ink`/`--c500-ink-soft`/`--c500-paper`/`--c500-paper-raised` become `--c500-text`/`--c500-text-soft`/`--c500-bg`/`--c500-bg-raised` — plain, theme-neutral names that don't imply a light physical writing surface that no longer exists in the design.

**Mana colors still reuse the ledger's own accents instead of introducing an independent WUBRG palette — same structure, muted execution.** `--c500-mana-g` (green/good) `#6b9080`, `--c500-mana-r` (red/bad) `#c17662`, `--c500-mana-gold` (multicolor/price-adjacent) `#c9a463` — desaturated, lower-contrast-with-itself versions of the original forest/rust/brass, not a new hue family. Alternative considered: give mana identity its own five fresh hues, fully decoupled from the status accents (the literal "Battlefield Rail" direction explored at the very start of this change). Rejected again, for the same reason as the first time — it would create two unrelated accent systems competing for the same visual weight, and the "in the red" / "in the black" pun stays load-bearing. Only white (`--c500-mana-w: #cfc6b8`), blue (`--c500-mana-u: #7897b3`), and black (`--c500-mana-b: #9b87a8`) are net-new tokens, tuned this round for ≥4.5:1 text contrast against `--c500-bg`/`--c500-bg-raised` (measured: green 5.0/4.6, red 5.1/4.7, gold 7.6/7.0, white 10.6/9.7, blue 5.9/5.4, black 5.5/5.0 — red, black, and colorless (`--c500-mana-c: #9a958a`, 6.0/5.5) were all retuned this round after measuring the first-draft hexes fell short).

**The "needs a keyline" problem moved from white to black — same principle, mirrored, not two unrelated fixes.** On the light parchment base, white was the mana color closest in value to the background (`#cbb98a` measured ~1.5:1 against `--c500-paper`) and needed deepening plus an ink-toned keyline to stay legible. On the dark base, the equivalent problem hue is black (`#6b5b73` first-draft measured 2.87:1 against `--c500-bg` — below even the 3:1 UI-graphic floor). Same fix, mirrored: `--c500-mana-b` gets lightened to `#9b87a8` (5.5:1, comfortably clears text contrast on its own) and additionally keeps a keyline — now a light, `--c500-text`-toned stroke instead of a dark `--c500-ink`-toned one — since a color sitting near the background's own value benefits from a crisp edge even once its raw contrast number clears the bar.

**The "ledger tape" is a layout consolidation, not a component merge.** `BudgetGauge`, `CardCountGauge`, `LegalitySummary`, and `ExportMenu` stay independent React components with their own props/tests; only their container changes from a stacked sidebar to a horizontal strip (flex row, each component's internal markup restyled to a compact inline form rather than today's stacked block). Alternative considered: collapse all four into one new `LedgerTape` component owning all their data. Rejected — the four draw from unrelated computations (budget, card count, legality, export text generation) and merging them would force one component to own four independent concerns purely for a layout win; a CSS/layout-level consolidation gets the same visual and space result without that coupling, and keeps existing unit tests (`BudgetGauge.test.tsx`, etc.) valid.

**The color-identity rail is a pure CSS/props addition on `CardRow`/`CardVisualTile`, derived from data already present.** Mapping: single entry in `colorIdentity` → that mana hue; length > 1 → `--c500-mana-gold`; length === 0 → `--c500-mana-c`; `enrichment` not yet resolved → neutral `--c500-line` (no color, no flash-then-recolor once Scryfall data arrives). No new fetch, no new field on `DeckCard`.

**Commander gets a dedicated hero region in `TabRoot.tsx`'s layout, not a new art-loading path.** The hero block reuses `CardVisualTile`'s existing artwork resolution (`resolveCardArt`) at a larger size via a size variant/class, rather than a parallel image-loading implementation — so the placeholder-on-missing-artwork behavior required by `card-visual-view`'s spec keeps working for free.

**The hero block always renders in Visual form, independent of the List/Visual toggle — a disclosed exception to `card-visual-view`'s existing requirement, not an incidental side effect.** That requirement's literal text says the toggle applies "to all zones at once." Walking its scenarios against the implementation surfaced the conflict directly: forcing the commander into hero art any time List is active is the point of the hero treatment, so the alternative — letting the toggle collapse the commander back to a plain row — was rejected as undermining the signature element for half of the toggle's states. `card-visual-view`'s spec now carries a matching delta narrowing that requirement to Deck Principal and Maybeboard, with Comandante/Comandante Parceiro's always-Visual behavior stated as its own scenario, rather than leaving the discrepancy undocumented.

**Deck Principal sits beside the Commander hero column, not below a full-width hero+analytics band — a direct fix for a real usability problem surfaced in live review.** The original layout put a full-width Commander-hero-plus-analytics row above the zones grid, which pushed Deck Principal (routinely ~90-100 rows) below the fold on a typical viewport. The revised layout makes Deck Principal a same-height sibling of a left column holding Comandante, Comandante Parceiro (side by side), and Maybeboard beneath them, so Deck Principal starts at the same vertical position as the hero column, not after an entire extra hero+analytics row. The analytics band (Curva/Cor/Tipo) moves below this main content row instead of above it — it's supporting information, not something that needs to be visible without scrolling the way the card list itself does.

**The Commander hero column widens enough to hold Comandante and Comandante Parceiro side by side, rather than stacked.** Alternative considered: keep them stacked (as originally built) to preserve a narrower column and a wider Deck Principal. Rejected per direct feedback — a partner-commander pair reads more like a single "who is this deck" statement side by side than as two sequential entries, and the column width lost to this is recovered by moving the analytics band out of this row entirely (see above), so Deck Principal doesn't end up meaningfully narrower for it.

**View-mode toggle becomes icon-only, with the accessible name moved from visible text to `aria-label`.** The Lista/Visual buttons' visible text was also their accessible name; switching to icons removes that, so each button needs an explicit `aria-label` (e.g., "Ver em lista" / "Ver em modo visual") to keep it announced correctly — icons are decoration for a sighted user, not a substitute for an accessible name.

**The default (non-hero) tile art size grows for readability, which also grows the shared List-mode hover preview.** `CardHoverPreview` (in `CardRow.tsx`) explicitly reuses `.c500-tile__img`/`.c500-tile__placeholder` "for a consistent look with Visual view" — so enlarging the base `.c500-tile__art` dimensions enlarges both surfaces from one change, rather than needing two independent size bumps that could drift apart.

**Dead `.c500-panel` overlay CSS is deleted; its two still-used sub-classes are renamed into the surviving component's own namespace.** `c500-panel__mark` → `c500-tab__mark`, `c500-panel__format` → `c500-tab__format-select`, moved under `.c500-tab__header`'s own rules. This removes the misleading implication that a "panel" still exists anywhere in the product.

**Typography drops to a single grotesk for every role, still on system-font stacks.** `--c500-font-display` (`ui-serif, Georgia, "Times New Roman", serif`) is removed; zone headers, chart titles, and the page title all move to `--c500-font-body`, the existing system sans stack — `--c500-font-mono` is untouched, still doing the tabular-numerals job it always did. This reverses the earlier decision to lean harder into the serif for distinctiveness: a serif/sans pairing reads as editorial and traditional, at odds with "modern and minimalist," and a single well-weighted grotesk is how most contemporary minimal app UIs (the reference point for this pivot) carry type character — through weight, scale, and spacing on one family, not through a second typeface. Still no bundled or CDN-loaded font, for the same dependency-surface reason as before.

**Name captions leave non-hero Visual-mode tiles, but stay on the hero and on any placeholder.** Deck Principal/Maybeboard tiles rely on artwork alone (the name stays as `alt` text for accessibility); the Commander hero keeps its caption since it is the deck's one named, singular identity rather than one of ~90 interchangeable grid entries. The "missing artwork degrades to a placeholder" requirement is untouched — a card whose art can't be resolved still needs *some* identifying content, so the placeholder keeps showing the name regardless of hero/grid. `card-visual-view`'s spec carries a second `MODIFIED Requirements` block for this, alongside the existing view-toggle exception.

**A dedicated `--c500-price` token, not a reused `--c500-mana-gold` — kept decoupled even now that gold itself clears contrast comfortably.** On the dark base, `--c500-mana-gold` (`#c9a463`) measures 7.6:1/7.0:1 against `--c500-bg`/`--c500-bg-raised` — high enough that reusing it directly for price text would no longer fail a contrast check the way the original light-theme gold did (`#a97728` at exactly 3.0:1 against `--c500-paper`, the reason `--c500-price` was split out in the first place). The token stays separate anyway: price and "this card is multicolor" are different semantic concerns that happen to share a color family, and decoupling them means a future tune to either one (for whatever reason) can't accidentally drag the other along. `--c500-price` is now `#d1a866` — close to gold, distinct enough to keep its own identity, still applied only to `.c500-card__price`/`.c500-tile__price`.

**The ledger tape drops its vertical divider lines; the absolute-positioned overlay chips (quantity input, remove button) flip from a light to a dark translucent background.** `.c500-tab__ledger-tape`'s `border-left` between items is removed — spacing alone now separates budget/count/legality/controls/export, in keeping with the minimalist direction; the gap widens slightly to compensate for the lost visual separator. Separately, `.c500-tile__qty`/`.c500-tile__remove` sit on top of card artwork and used a light `rgba(247, 240, 222, 0.9)` chip background matched to the old parchment tone — on the dark base this becomes a dark `rgba(23, 23, 27, 0.85)` chip (matching `--c500-bg`), so these controls don't look like a stray light-mode leftover floating on dark artwork.

**Analytics moves from a full-width band to a third column — its charts stack vertically instead of sitting side by side.** The three `BarChart` instances no longer have the horizontal room a full-width row gave them, so `.c500-tab__analytics` changes from a wrapping horizontal flex row to a vertical stack, each chart at the column's full width. `.c500-tab__body`'s side padding shrinks and its `max-width` grows so three columns (hero column, Deck Principal, analytics) fit without feeling cramped on a typical desktop viewport.

**Companheiro reverts to stacking below Comandante, with its side-by-side sizing (`flex: 1 1 140px`) undone, plus a new shrink-when-empty state.** `ZoneSection` already receives `cards`, so `cards.length === 0` drives a compact-empty modifier class on the hero zone specifically for Companheiro (Comandante itself is never legitimately empty in a captured deck, so this state is scoped to the partner slot): the dropzone's min-height collapses to a small "drop a partner here" hint instead of reserving full hero-art height, and expands back once a card is present. Pure CSS/class-driven, no new data.

**Deck Principal's List view gets CSS multi-column grouping (Moxfield-style), scoped to Deck Principal only.** Each type/color/cmc group's wrapper gets `break-inside: avoid-column` inside a `column-width`-based container on the dropzone, so a group's cards stay together within one column while groups flow left-to-right filling the available width — the same shape as the Moxfield reference, achieved with plain CSS multi-column rather than a hand-rolled column-placement algorithm. Maybeboard, now living in the narrow hero column, keeps its existing single stacked list — multi-column needs width Maybeboard's column doesn't have.

**The Comandante zone loses its removal control via prop omission, not a new "non-removable" flag threaded through the component tree.** `CardVisualTile`'s remove button already renders conditionally on `{onRemove && (...)}` (`CardVisualTile.tsx`) — so `TabRoot` simply not passing `onRemoveCard` when it renders the Comandante `ZoneSection` is sufficient; no new prop, no new branch in `CardRow`/`CardVisualTile`/`ZoneSection`. `deck-organizer`'s "Explicit card removal" requirement ("the user SHALL be able to remove **any** card") is directly contradicted by this and needs a matching delta, drafted for `specs/deck-organizer/spec.md` but not yet written — that capability has no delta file in this change yet, and creating one is `/opsx:continue`'s job, not this update's.

**Status-tint backgrounds (active dropzone, error message) move from pastel to translucent-dark.** `--c500-status-good-soft`/`--c500-status-bad-soft` were solid light pastels (`#dfeee6`/`#f6e3df`) derived from the light-theme forest/rust — a pastel tint reads as washed-out rather than "quiet" on a near-black base, so both become low-alpha overlays of the new green/red instead: `rgba(107, 144, 128, 0.16)` and `rgba(193, 118, 98, 0.16)`. Alpha-based rather than a second set of solid hex values, so they automatically stay coherent with whatever the base green/red end up tuned to, without a separate manual pairing to keep in sync.

**The Comandante's quantity field needs no code change — it's already structurally impossible.** `isBasicLand()` gates the quantity input in both `CardRow` and `CardVisualTile`, and a legal Commander can never be a basic land, so "the commander should not be editable" is already vacuously true. Adding a defensive check anyway would be validating a scenario that can't happen.

**The ledger tape and the analytics column become sticky; the hero column does not.** `.c500-tab__ledger-tape` gets `position: sticky; top: 0` plus a `z-index` high enough to sit above the content scrolling up beneath it — its background is already opaque (`--c500-bg-raised`), so nothing bleeds through. `.c500-tab__analytics` gets `position: sticky` with a `top` offset that clears the tape's height, so it stays visible beside Deck Principal (the tallest column) as the page scrolls. The hero column (Comandante/Companheiro/Maybeboard) is deliberately excluded — the request named the charts and the top row specifically, not it, and unlike the tape and the charts it isn't a toolbar or reference panel the user needs while scanning a 99-card list.

**The analytics column has genuine room to stick, because `align-items: start` shrinks the item, not its grid area.** This is worth stating explicitly since it's not obvious from reading the CSS: `.c500-tab__main-row`'s single row track sizes to its tallest item (Deck Principal, ~99 rows), and `align-items: start` only changes how the analytics item is *aligned and sized within* that row's height — it does not shrink the row track itself. The analytics column's containing grid area is therefore just as tall as Deck Principal's, which is exactly the room `position: sticky` needs to stay pinned as the page scrolls past it. If a future change switched `.c500-tab__main-row` to per-item auto-sized rows (e.g., separate implicit rows instead of one shared row), this mechanic would break and sticky would have nothing to stick within.

**Sticky analytics only applies at the >=1200px breakpoint where analytics is a real third column.** Below that width, the existing `grid-column: 1 / -1` rule already drops analytics to a full-width block beneath the hero column and Deck Principal (not beside anything tall) — sticky has no meaningful effect there and is left off, rather than sticking to an arbitrary position with nothing tall left to scroll past.

**A user-selectable sort axis replaces the old automatic two-axis tiebreak, rather than adding price as a third dimension on top of it.** The original "Grouping and sorting" requirement sorted a group's cards by *both* non-grouping axes in a fixed priority (e.g., grouped by Type → sorted by Color then CMC then name). Bolting price on as a fourth automatic tiebreak would make an already-implicit ordering even less predictable to a user who can't see the rule. Replacing it with one explicit, user-chosen axis (mana value, name, color, or price) is simpler to implement, simpler to explain, and directly answers the actual ask ("order by card value") instead of hiding price inside a longer automatic chain. Name is kept as the universal tiebreak for stability — without it, cards tied on the active axis (e.g., two cards at the same CMC) would have no defined relative order.

**Each sort axis gets one fixed, sensible direction — no separate ascending/descending toggle.** Mana value ascends (matches today's existing default reading), name is alphabetical, color follows the same colorless/W/U/B/R/G/multicolor order already used everywhere else in this system, and price descends (highest first, confirmed directly — useful for spotting what's driving the budget). Exposing a direction toggle per axis wasn't asked for and would double the control's surface for a benefit nobody requested.

**Unresolved-price cards sort last under Price, not first and not interleaved by guesswork.** A card with no resolved price isn't "free" (budget-tracking already treats unresolved prices as "incomplete," never as R$0) and isn't necessarily cheap or expensive — sorting it after every priced card avoids implying a value it doesn't have, while still giving it a defined, stable position (via the name tiebreak) rather than leaving its placement undefined.

**The budget meter shows both used and remaining, not just the total spent.** Replacing "R$414,27 · de R$500,00 de limite" with an explicit used/remaining pair (e.g., "R$414,27 usados · R$85,73 restantes") answers the actual question a budget-conscious deckbuilder asks while shopping: not just "what have I spent" but "what do I still have to spend." The over-cap visual state and exact-overage figure (`BudgetGauge`'s existing `isOverCap`/`overAmount` handling) are unchanged — this only touches which two numbers are shown day-to-day.

**Group labels gain a count and a larger, higher-contrast treatment, mirroring the zone header's own `(N)` pattern rather than inventing a new one.** `.c500-zone__header` already shows a card count next to the zone name (e.g., "Maybeboard (80)"); `.c500-group__label` (e.g., "CRIATURA") gets the same treatment for consistency, computed from `group.cards` exactly the way the zone-level count is computed from `cards` — no new counting logic, just the same reduction run at a smaller scope.

**The mana curve chart drops land cards instead of bucketing them at CMC 0 alongside genuinely free spells.** A land card's converted mana cost is 0, but that 0 doesn't mean the same thing a 0-cost artifact or spell's does — mixing them into one bucket makes the curve look like it has a large "free spells" spike that's actually just "how many lands are in the deck," a number the deck's total card count and mana-base composition already convey elsewhere. Filtering land cards out of `manaCurveBuckets()` (via the same `primaryType() === "Land"` check `group-sort.ts` already uses for type grouping) makes the curve chart about spells' costs again.

**The color chart's new "Terrenos" bucket separates land cards from color-identity buckets entirely, rather than color-coding them.** A dual land's color identity (e.g., both green and white) is real information for deck-building legality and mana-base planning, but it isn't the same kind of fact the rest of the chart conveys ("how many green spells, how many blue spells..."). Pulling every land into one dedicated bucket — regardless of its own color identity — keeps the remaining color buckets meaningfully about *spells*' colors, and keeps the chart's total count still equal to Main Deck's total (every card falls into exactly one bucket: Terrenos if it's a land, otherwise its color-identity bucket).

**"Terrenos" gets its own token, `--c500-mana-land: #a68a6b`, rather than reusing `--c500-mana-c` (colorless).** Colorless non-land cards (artifacts, colorless spells) and lands are conceptually different categories that now sit as separate bars in the same chart — sharing a color between them would make the two bars visually indistinguishable at a glance, defeating the point of splitting them out. `#a68a6b` is a muted earth-brown (5.5:1 / 5.1:1 against `--c500-bg`/`--c500-bg-raised`), distinct from both the existing gold (more saturated, yellow-leaning) and white (lighter, cooler) tokens it sits near in the palette.

## Risks / Trade-offs

- **[Risk]** A colored rail on every one of ~90–100 card rows could read as visual noise rather than signal. → **Mitigation:** keep the rail thin (2–4px) and confined to the row's edge, never a full-row background tint; it reads as texture at a glance and as information on inspection, the same way a real card's frame border does.
- **[Risk]** `--c500-mana-b`'s keyline may still under-perform on contrast in practice even after lightening the base tone (the same risk `--c500-mana-w` carried against the original light-parchment base — resolved there, now mirrored onto black against the dark base). → **Mitigation:** spot-check contrast during implementation against `--c500-bg` and `--c500-bg-raised`; adjust the tone or keyline weight then rather than treating the computed hex as final. The retunes already applied to red/black/colorless this round (see the "needs a keyline" decision above) came from exactly this kind of check, not from the first-draft hex guesses.
- **[Risk]** Reusing forest/rust for both mana identity (on the card rail) and status (on the gauge/legality/error states) could read as contradictory — e.g., a green-identity card sitting inside an over-budget (rust-toned) ledger tape. → **Mitigation:** the two systems never occupy the same UI region (rail is per-card-edge only; status color only appears in the ledger tape, gauge fill, and error states), so they stay spatially distinguishable; call this out with the same kind of inline CSS comment the current file already uses to document non-obvious intent.
- **[Risk]** Restructuring `TabRoot.tsx` and consolidating four sidebar components into one strip touches a lot of existing markup that component and integration tests assert against. → **Mitigation:** component-level tests (`BudgetGauge.test.tsx`, `CardRow.test.tsx`, etc.) keep asserting on each component's own props/output and mostly don't need changes; only tests asserting on `TabRoot`'s overall DOM shape or sidebar structure need updating, which tasks.md accounts for explicitly.

- **[Risk]** Enlarging the default Visual-mode tile size means fewer tiles fit per row, so a ~90-card Deck Principal in Visual mode scrolls further within its own zone. → **Mitigation:** accepted trade-off — the explicit ask was readability over density; List mode (the default view) is unaffected by tile size at all.
- **[Risk, superseded]** Moving the analytics band below the main content row meant it was no longer visible without scrolling. → This described the round-1 layout (analytics as a full-width row below everything); round 2 (task 8.5) already moved analytics to a third column beside Deck Principal instead, and this round makes that column sticky — analytics is now visible *without* scrolling away at all, the opposite concern from what this risk described. Left here rather than deleted, so the layout's history stays legible.

- **[Risk]** CSS multi-column layout can visually reorder content in ways that don't match reading order for screen-reader/keyboard users (columns fill top-to-bottom-then-left-to-right in the DOM, but multi-column rendering can make the visual flow read left-to-right-then-top-to-bottom). → **Mitigation:** each column holds one complete, self-contained group (`break-inside: avoid-column` keeps a group from splitting), so within a group the reading order is still correct; only the group-to-group order could visually differ from DOM order, which is a much smaller mismatch than reordering individual cards would be.
- **[Risk]** Losing the Comandante's removal control could strand a user who captured the wrong card as commander, since deck-organizer's existing "Commander zone cardinality" rule rejects dragging a second card directly onto an already-occupied Comandante (verified against `openspec/specs/deck-organizer/spec.md`'s scenario) — so a naive "just drag the replacement in" mitigation would be false. → **Mitigation:** the correct recovery path is two ordinary drag moves, both already supported today: drag the wrong card out of Comandante into any other zone (freeing the slot), then drag the intended commander in. No removal control is needed for either step.

- **[Risk]** A sticky ledger tape without a high-enough `z-index` could let scrolling content (card rows, chart bars) render on top of it instead of behind it, especially since the tape overlaps the hero column and Deck Principal vertically once pinned. → **Mitigation:** give the tape an explicit `z-index` clearly above the zones/analytics content; its background is already opaque, so once stacking order is correct nothing shows through.

- **[Risk]** Replacing the automatic two-axis tiebreak with a single user-chosen sort axis is a real behavior change: cards that used to be implicitly tie-broken by a second dimension (e.g., Type-grouped cards also ordered by color) now only tie-break by name once the chosen axis is exhausted. → **Mitigation:** this is the intended trade — explicit, visible user control in exchange for the old invisible multi-axis rule — and name as a stable tiebreak means results are still fully deterministic, just along one axis instead of two.
- **[Risk]** Splitting lands into their own "Terrenos" bucket needs the color-distribution chart's bucket counts to still sum to Main Deck's total card count, or the chart would silently undercount/overcount. → **Mitigation:** every Main Deck card falls into exactly one bucket by construction (Terrenos if `primaryType() === "Land"`, otherwise its existing color-identity bucket) — mutually exclusive and collectively exhaustive by the same logic already governing the type/color grouping elsewhere, not a new invariant to maintain separately.

## Migration Plan

This is a browser extension with no persisted-data shape change (no storage format, no message-protocol change) — only CSS and component markup change. "Deploy" is shipping the next extension version; "rollback" is reverting the commit(s) and shipping the prior version, with no data migration or feature flag needed either direction.
