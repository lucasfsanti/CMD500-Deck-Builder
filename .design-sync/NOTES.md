# design-sync notes — CMD500 Deck Builder

## Repo shape

This repo is a single Chrome-extension app (CMD500 Deck Builder), not a
published component library — there is no root `package.json`, no
Storybook, and `extension/src/ui/components` was never meant to be
consumed outside this extension. At the user's explicit request, a new
package (`design-system/`) was created specifically to give design-sync
something to import: `design-system/src/index.ts` **re-exports the real
components and domain types straight from `extension/src/...` by relative
path** — no duplication, no reimplementation. Anything that changes in the
extension's real components is picked up automatically on the next
`design-system` build.

## Build

- `design-system/package.json` → `cmd500-design-system`, private, built
  with `npm run build` (esbuild bundle + `tsc --emitDeclarationOnly`).
- `cfg.pkg` / `--entry` point at `design-system/dist/index.js`; `cfg.tsconfig`
  is `tsconfig.json` (package-relative — do NOT prefix with `design-system/`,
  the build resolves it from `PKG_DIR` already).
- **`cssEntry` must resolve inside `design-system/`** (design-sync enforces
  this — it's uploaded verbatim). `design-system/scripts/build.mjs`
  therefore copies the real `extension/src/ui/panel.css` into
  `design-system/vendor/panel.css` on every build; `cfg.cssEntry` points at
  that generated copy. `design-system/vendor/` is gitignored (regenerated
  output, never hand-edited).

## Known render warns

- `[FONT_MISSING]` for "Cascadia Code": `--c500-font-mono` is a **system
  font stack by design** (`panel.css`'s own header comment: "Both are
  system-font stacks — no bundled or CDN-loaded typeface"). No `@font-face`
  should ever be added for this — the DS pane rendering it with system
  fonts is the correct, intended behavior. Not a gap to fix on re-sync.

## Previews

- All 11 components have authored previews in `.design-sync/previews/`,
  each importing shared sample-deck fixtures from
  `.design-sync/previews/_fixtures.ts` (one small internally-consistent
  "sample deck" so price/legality/mana-identity agree across every
  component's stories). The converter ignores `_fixtures.ts` itself (only
  `<Name>.tsx` files become components) — safe to keep adding shared
  helpers there.
- `CardRow`, `CardVisualTile`, and `ZoneSection` need a `DndContext`
  ancestor (dnd-kit) to render their sortable/droppable hooks without
  warnings — every preview wraps in one; do the same for any new story.
- `ManaCostIcons` hotlinks real icons from `ligamagic.com.br` at render
  time (by design — see its JSDoc, no bundled copy). The render check and
  grading both passed with real network access to that host; if a future
  re-sync runs somewhere without outbound network, those icons will show
  broken-image glyphs instead of a component defect.
- `cfg.overrides`: `ZoneSection`, `ExportMenu`, `CardRow` are all
  `cardMode: "column"` — they're full-width components that overflowed the
  product's grid cells at the default card width ([GRID_OVERFLOW]). Any
  new component in the same "wide row" family should probably get the same
  override proactively.

## Re-sync risks

- The design-system package is a thin re-export shim. If a component's
  source file moves or is renamed inside `extension/src/ui/components/`,
  `design-system/src/index.ts`'s import paths need updating by hand — the
  build will fail loudly (missing module) rather than silently drifting, so
  this is safe but not automatic.
- `design-system/vendor/panel.css` is regenerated by `npm run build` in
  `design-system/` — always rebuild the package before re-running the
  converter, or the CSS copy can go stale relative to the real
  `extension/src/ui/panel.css`.
- Re-sync command (from repo root, after re-copying staged scripts and
  reinstalling `.ds-sync/node_modules` on a fresh clone):
  ```sh
  npm run build --prefix design-system
  node .ds-sync/resync.mjs --config .design-sync/config.json \
    --node-modules ./design-system/node_modules \
    --entry ./design-system/dist/index.js --out ./ds-bundle \
    --remote .design-sync/.cache/remote-sync.json
  ```
  (fetch `_ds_sync.json` from the project into that `--remote` path first —
  see base SKILL.md §"Re-syncs are one command".)
- playwright is pinned to `1.62.0` in `.ds-sync/` specifically because the
  machine that ran the first sync had chromium build 1234 already cached
  under a different playwright install; a future sync on a different
  machine should just install whatever playwright version is current and
  let it fetch its own matching chromium build.
